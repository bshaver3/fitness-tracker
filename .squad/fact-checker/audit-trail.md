### 2026-11-14 — PR #8 Daily Calorie Tracker pre-mortem (DA)
Advisory: strongest concern is false confidence at the API boundary: `/food-target` PUT/GET responses are `{}` and PUT accepts an open-ended object, while `FoodTracker.js` assumes `{daily_calorie_target}` succeeds and reports success after any 2xx; `DailyFoodSummary.status` is an unconstrained string and unknown statuses fall through to “at your daily target.” A plausible 30-day failure is a backend request-field/summary-status drift silently producing a success toast or false at-target statement. Assumptions: target is a deliberate user choice (no recommendation), backend implements the untyped target contract as the UI assumes, and summary arithmetic/status stay mutually consistent. Alternative: contract-test request/response semantics and enumerate `status` (including exact match), or render comparison from validated total/target arithmetic. Math/ranges: PRD requires total=sum(entry calories), remaining=target−total below target, over=total−target above, no negative remaining; UI currently trusts API values/status instead of computing. UI and OpenAPI bound entry/target inputs to integer 1–10,000 (FoodTracker.js:88,162; openapi.json FoodEntry 185–191 and daily_calorie_target 425–430); PRD only says positive whole number, so upper bound is implementation/API evidence, not product-confirmed. No auto-recommendation is verified (PRODUCT.md:57,107). No concrete blocker in DA mode; risk advisory.
